## 🔒 確定方針（2026-08-10 の設計相談で決定・経緯はリポ直下 CHANGELOG v233 参照）

- **別アプリにする**。あの日への同居・トップの切り替えボタンはやらない（核3要素「偶然/久しぶり/よみがえる」を全部逆向きに壊すため。あの日のローカル完結の約束も濁る）
- **データ共有は3段階の①②のみ**: ① OSの写真ライブラリが共通基盤（レシート写真のEXIF GPS含む） ② 日パック式のバージョン付きファイル契約で狭く受け渡し（あの日の位置ロガー軌跡→こちら / 日ごとの店名・金額→あの日）。**③ DBファイル直結はしない**（IndexedDBは物理的に共有不能・SQLite化後のApp Group共有もスキーマが2つのリリースtrainに跨る＝madeleine/spike二重管理でズレた失敗の再演）
- **AIへの窓口 = BYOK（ユーザー自身のAPIキー）**: ⚙で登録 → 撮ると端末から Anthropic API へ**直接**送信（サーバーなし・アプリ運営者はデータに触れない）。ブラウザ直接呼び出しは公式サポート（`anthropic-dangerous-direct-browser-access: true` ヘッダ / SDK の `dangerouslyAllowBrowser`）
- **「AIで直接アクセスできるリンク」はアプリではホストしない**（サーバーになるため）。代替: (a) OS共有シートでAIアプリへファイル直渡し（実装済） (b) ユーザー自身の Drive/iCloud に保存→そのリンクをAIへ（ユーザーのクラウドが運び役・アプリはサーバーレスのまま）
- **レシート写真が あの日 の山札を汚す問題**: native化時に専用アルバム（例「レシート」）保存＋あの日側でアルバム除外を足す（あの日の今の審査trainには入れない）

## ⚠️ web spike の同一オリジン注意

## 🔑 APIキーの置き場（2026-08-10 検討・ユーザー指摘「置き場はかえないといけないかも」への答え）

ライフログの置き場＝**キーはSupabase Secrets（サーバ）・ブラウザには合言葉(MAP_SECRET)だけ**。receipt-spike はサーバーレスなので同じ形は取れない。選択肢は3つ:

| 案 | キーの場所 | 漏れた時の被害 | 備考 |
|---|---|---|---|
| **A. BYOK・localStorage（現行・spike期間の採用案）** | ブラウザ（github.ioオリジン） | **金銭のみ**＝Console で失効可・支出上限で頭打ちにできる | ⚙に「専用キー＋支出上限」の運用ガイドを表示（r3）。native化で Keychain/SecureStorage へ＝製品の最終形 |
| B. ライフログの receipt 関数を窓口に（合言葉方式） | Supabase Secrets のまま | ブラウザに置くのは MAP_SECRET だが、**MAP_SECRET は位置履歴・日誌・収支の全権**＝漏れた時の被害は金銭でなく**プライバシー**で、Aより重い。新オリジンに置く＝露出面が広がる | さらに画像が Storage を経由（upload→extract→discard）＝ローカル完結の検証にならない。「今すぐ自分が使う」ならライフログ本体を使えばよい |
| C. スコープ付きトークン（ai関数の🔑方式をOCR専用に拡張） | Supabase Secrets のまま | OCR専用スコープ＝最小権限・失効可 | ライフログ側に1手必要。製品はどのみち A+Keychain になるので spike への投資としては過剰＝今はやらない |

**結論: spike期間は A を維持**。根拠＝(1) Anthropicキーは失効・支出上限で被害を金銭の上限内に限定できる（MAP_SECRET を新オリジンへ広げるより漏洩時の質が軽い）(2) B は画像がサーバ経由＝「ローカル完結・ストア配布できる形」という spike の検証目的が消える (3) 最終形は native の Keychain で確定しており、暫定に投資しない。
**⚠ 別件の重要制約（Aの弱点というより web spike 全体の弱点）**: iOS Safari は**7日間未訪問でサイトデータ（localStorage・IndexedDB＝キーもレシートも）を消し得る**（ITP）。**ホーム画面に追加**すると対象外になる → ⚙に案内表示（r3）・実機確認の最初にホーム画面追加を推奨。

## 📚 ライフログ（owntracks-supabase-notion）から移植した教訓（出典: 同リポ CLAUDE.md・receipt関数。実運用228枚・収支248行の実測）

- **撮影時のGPSは使えない**: 購入地点から中央値296m・平均4.0km・2km超が23%（レシートは後でまとめて撮るため）→ 位置の出どころは ①印字住所（OCRで拾う・ジオコーディングは後段） ②購入時刻±20分の動線（±20分に点が無ければ前後の点が250m以内=静止ならその位置・最大±12h）＝**あの日の位置ロガー軌跡を日パックで受ければ同じ補完がローカルで再現できる**
- **住所の印字は高解像度でしか読めない**: 4096pxで31%・1600pxでほぼ0% →「**縮小する前に取れる情報は全部取る**」（r2で送信2576px化）
- **1枚に複数レシート**が普通に起きる（r2で receipts 配列化）
- **交換フォーマットに統計は入れない**（生データからAIが計算・アプリ集計と二重実装しない）→ 書き出し v2 も生データのみ
- **レシート画像は「紙を捨てたら唯一の原本」**（写真と違い iCloud に原本が無い非対称）。⚠ web spike の `<input capture>` 撮影は写真アプリに残らない＝IndexedDB 内が唯一のコピー。**電帳法・確定申告に使う可能性があるなら紙は捨てない運用で**。native化の「写真フォルダに原本保存」が効くのはここ
- **支出マップの実装参考（次周回）**: 支出=金マーカー・金額で大きさ / markercluster でズーム連動集計（個別→地域合計→全体） / タイムライン=滞在+支払いを時系列 / 支出マップ表示中は他レイヤを自動オフ（閉じたら戻す・黙って消さない）

## 🧭 ライフログとの関係（要ユーザー判断・急がない）

ライフログ側には**レシート取り込み〜支出マップが既に本格稼働**している（サーバ側Claude・Supabase・合言葉認証・個人用）。一方 同リポ docs/porting-spec.md は native 製品化を **local-first（Free=端末完結・Pro=クラウド同期）** と決定済み。整理すると:

- 将来「レシート単体アプリ」として出すか「ライフログ native 製品の一部」へ合流させるかは、spike が当たってから決める（どちらに転んでも検証は活きる）
