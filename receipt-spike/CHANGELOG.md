## r4 — 📱 Android native 化で ITP を根本回避（Capacitor・直接APK配布） (2026-08-10)

**背景**
- r3 で見つけた **iOS Safari の ITP（7日間開かないとサイトデータを削除）** への対応。ユーザー判断＝「**対応だけしたい**。ネイティブアプリか、ログインか。ログインだとデータがサーバーに置かれる、それはまずい。Android端末を持つ知り合い向け、だから端末直接アプリインストール」。

**設計判断**
- **ログイン方式を却下**（ユーザー判断を支持）＝ ITP は「サイトデータを消される」問題であって「データが端末にある」ことが原因ではない。サーバーに逃がすと**ローカル完結という spike の検証目的そのものが壊れる**。native 化なら同じデータをアプリ領域に置くだけで解決＝方針を1ミリも曲げずに済む。
- **Capacitor で Android 化**。あの日の基盤（Capacitor 8・compileSdk 36・sync-web の流儀）をそのまま踏襲、ただし **appId・アプリ名・android プロジェクトは完全に別**（v233 の「別アプリ」決定どおり）。
- **CAMERA 権限は宣言しない**。Capacitor の `BridgeWebChromeClient.isMediaCaptureSupported()` を読んで確定＝`hasPermissions(CAMERA) || !hasDefinedPermission(CAMERA)`。つまり**宣言しなければ許可不要**でOSのカメラアプリを intent 起動できる。宣言すると実行時許可が必須になり、要求コードを持たないこのアプリでは撮影が壊れる。**権限は INTERNET のみ**＝知り合いに配る時の説明も簡単。
- **配布は debug APK の直接インストール**。サイドロードに署名の種類は関係なく、リリース鍵の管理が消える。⚠ 更新時は versionCode を上げる／同じPCでビルドする（署名が変わると上書き更新できない）。
- **📋 コピー書き出しを追加**。native WebView は `<a download>` も Web Share API も効かない可能性がある＝データが端末に閉じ込められるのが最悪のシナリオなので、クリップボードという**必ず効く逃げ道**を先に用意した（プラグイン不要）。

**調べたこと（Android デベロッパー確認）**
- あの日の TODO に「2026年9月までに登録しないと認定済み端末にインストール不可（＝Play 以外で配信するアプリの話）」というメモがあり、**まさに今その"Play 以外で配信"を始める**ので確認した。結果＝**開始は 2026-09-30 でブラジル/インドネシア/シンガポール/タイのみ・グローバルは2027年**、かつ**確認済み開発者は直接配布の自由を維持**。オーナーは 2026-07-10 に本人確認済み → **当面そのまま通る・日本は第一弾外**。将来は Play Console で「Play 外配信アプリ」として登録すれば継続できる。

**教訓**
- **制約に見えたものが方針を変えさせるとは限らない**。ITP は「サーバーに置け」という圧力に見えるが、実体は「ブラウザの器を使うな」でしかなかった＝器を変えるだけでローカル完結を守れた。制約を読むときは**それが本当に何を禁じているか**まで降りる。
- 権限は「足す」より「足さない方が動く」ことがある（CAMERA）。フレームワークの実装を読んで確かめる価値があった。

**残課題 / 次の方向**
- **実機で4点確認**（撮影が開くか／分析／**書き出し3手段のどれが効くか**／数日後もデータが残るか）。書き出しが全滅なら Share/Filesystem プラグイン導入を r5 で。
- iOS は当面ブラウザ版＋ホーム画面追加で回避（native iOS は配布が重い）。

## r3 — OCRルールをライフログから移植＋APIキーの置き場を決定 (2026-08-10)

**背景**
- ユーザー指摘「BYOK窓口もライフログに実装済み＝参考に。APIキーの置き場はかえないといけないかも」→ ライフログの receipt 関数を精読。キーの置き場＝**Supabase Secrets（サーバ）＋ブラウザは合言葉のみ**、OCR＝**実運用で磨かれた system プロンプト**（和暦・明細全行・住所の厳密ルール）と判明。

**設計判断**
- **OCR_SYSTEM のルール群を system プロンプトとして移植**（布石フィールド＝インボイス/税内訳ぶんは除く＝spike の核ではない・出力トークン節約。将来必要になったらスキーマごとライフログから移植）。強制ツール方式は採らず structured outputs（json_schema）を維持＝保証は同等でコードが短い。
- **キーの置き場は「spike期間は現行A（BYOK・localStorage）を維持」と決定**。A/B/C の比較と根拠は TODO.md「🔑」に記録。要点＝ライフログ方式(B)をなぞると MAP_SECRET（位置履歴の全権）を新オリジンに置くことになり、漏洩時の被害の質が金銭→プライバシーに悪化する。運用ガードとして⚙に「**専用キーを発行し Console で支出上限**」を明示。
- **iOS Safari の ITP（7日未訪問でサイトデータ削除）を⚙で警告**＋ホーム画面追加を案内。キーだけでなく**レシートデータ本体が消え得る**＝web spike 最大の実務リスク（ライフログはサーバが真実なので無縁だった。local-first ゆえの新しい弱点）。

**教訓**
- 「同じBYOK」でも置き場の文脈が違う: サーバありなら Secrets が正解・サーバーレスなら「失効できて被害上限を設定できる資格情報を、最小の露出で」が判断軸。資格情報は種類ごとに漏洩時の被害の質（金銭/プライバシー）で比べる。

**残課題 / 次の方向**
- 実機一周（ホーム画面追加まで含めて）。位置補完・支出マップは次周回（TODO参照）。

## r2 — ライフログ実装の教訓を反映（複数レシート・印字住所・高解像度OCR・カテゴリ統一） (2026-08-10)

**背景**
- ユーザーがライフログ（owntracks-supabase-notion）のリポを共有。読むと**レシート取り込み〜支出マップが既に本格稼働**しており（receipt Edge Function＝Claude OCR・transactions テーブル・地図重ね）、実運用228枚分の実測教訓が濃かった。**データが1件もない今がスキーマ修正の最安タイミング**なので即反映。

**設計判断（すべてライフログの実測が根拠）**
- **1枚に複数レシート**: スキーマを `receipts` 配列に。一覧・書き出しは「写真×レシート」に展開（「📷内 1/2」表示・過去の単体形式も receiptsOf() で吸収）
- **印字住所を拾う**: 撮影時GPSは購入地点から中央値296m・2km超23%ズレる（後でまとめて撮るため）→ 位置の出どころは印字住所。住所は1600pxではほぼ読めない（4096pxで31%）→ **OCR送信・保存を1568→2576px（high-res上限）に**。保存も2576px＝再分析でも住所が取れる
- **カテゴリをライフログの transactions と同一セットに**（食費/外食/日用品/交通/医療/衣類/娯楽/その他）＝将来の日パック受け渡し・支出マップ流用でマッピング不要。currency は廃止（円整数に統一・ライフログと同じ）
- kind=expense/income 追加（返金・受取＝一覧で緑・+表示・月合計は支出のみ）。store/branch 分離（チェーン名と支店）
- 書き出し version 2: レシート単位にフラット化（photo_id で写真に紐付け）・統計は入れない（生データからAIが計算＝ライフログの交換フォーマット方針を踏襲）

**教訓**
- **同じ問題を先に解いた自分の実装が最強の参考資料**。スキーマはデータゼロのうちに直す（後からだと移行が要る）
- コスト影響: 2576px送信で画像≈4800トークン＝Opus 5 で約5円/枚（⚙の目安表記も更新）。住所が取れる価値との交換で採用

**残課題 / 次の方向**
- 実機一周（r1から持ち越し）。位置補完（±20分動線・静止250m/±12hルール）は日パック契約の設計時にライフログから移植。ライフログとの関係整理は TODO.md「🧭」

## r1 — 撮る→自動AI分析→一覧→期間書き出し (2026-08-10)

**背景**
- 「あの日」の設計相談から派生。レシートを写メ→詳細がたまる→AI分析→統計地図分析、をやりたいが、核3要素（偶然/久しぶり/よみがえる）と正面衝突するため**別アプリ**と決定（経緯はリポ直下 CHANGELOG v233・確定方針は本フォルダ TODO.md）。
- まず web spike で「撮る→自動で読める→取り出せる」の一周が気持ちいいかを確かめる。

**設計判断**
- **BYOK直接送信**: ユーザーのAPIキーで端末→Anthropic API へ直接 fetch。サーバー・中継なし。CORS は公式オプトイン（`anthropic-dangerous-direct-browser-access: true`）。SDKもバンドラも使わない生 fetch（単一HTMLファイル・CDN依存ゼロの流儀を踏襲）。
- **structured outputs（output_config.format=json_schema）**で店名/日付/合計/通貨/カテゴリ/支払/品目を抽出。プロンプトで形式を頼むのではなくAPIレベルでスキーマ保証＝JSON.parse が落ちない。nullable は anyOf で表現（type配列は仕様上未保証のため）。
- **モデルは⚙で選択**（既定 Opus 5 / Sonnet 5 / Haiku 4.5）。コスト目安を選択肢に併記（1568px縮小で画像≈1600トークン→Opus5で2〜3円/枚）。effort=low を付与（Haiku 4.5 は effort 非対応のため除外分岐）。
- **接続テストは count_tokens**（無料エンドポイント）＝キー検証に課金させない。
- **画像は1568px長辺に縮小して送信**（visionの推奨解像度・トークン最小化）。保存も縮小後のみ（原本は端末の写真アプリに残る前提）。
- 一覧の並びは**レシート記載の日付**（撮影日ではなく）。月グループ＋月合計（JPYのみ合算）。
- 書き出しは**バージョン付きJSON**（`format: receipt-spike-export, version: 1`）を正とし、CSV(BOM付き)とOS共有シートを添える。共有シートがAIアプリへの「渡し口」＝リンクのホストはしない。

**ハマり回避（あの日の教訓を先回りで適用）**
- `createImageBitmap` 不使用 → `<img>`+`<canvas>`+`URL.createObjectURL`（+必ず revoke）。
- `e.target.value = ''` は `finally` で（await 前に消すと File 参照が無効化される疑い）。
- IndexedDB/localStorage は同一オリジンで あの日 web と共有 → `receipt-spike` / `rcpt.*` で名前空間分離。

**結果 / 観察**
- preview 未確認・実機未確認（このセッションは remote 環境）。**次セッション: 実機 iPhone Safari で一周通すのが最初の仕事**。

**残課題 / 次の方向**
- 実機確認 → FBを r2 へ。支出マップ（Notion ライフログ構築メモの家計簿/日誌構想を参考）はデータが溜まってから。
- APIキーの置き場所: web spike は localStorage（XSS面は単一ファイル・外部依存ゼロで緩和）。native化時に SecureStorage へ。
