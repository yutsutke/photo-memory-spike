## r64 — 🎉実機で共有シートが刺さった／余計な「レシート.txt」を消した (2026-08-15)

**背景**
- r63 の実機確認＝ユーザー報告 **「ワンタップで CSV ファイルを Google ドライブに送れました」**＝**共有シート方式が当たり**（r63 で「指で触る画面では共有シート」に倒した判断が実機で報われた）
- 🎉 さらに発見＝**「ファイルの送り先を直接クロードにも送れました」**＝**Drive を経由せず AI アプリへ手渡しできる**。r62 で作った「📤 → Drive → AI が読む」より**さらに一手短い道**が、同じ共有シートの中にあった
- 🐛 ただし **「ファイルが3つあった。レシート.txt が余計」**（2つのはずが3つ）

**ハマったところ**
- 症状: 共有シートで CSV 2つを送ると、**3つ目に「レシート.txt」が付いてくる**
- 原因: `navigator.share` に **`files` と一緒に `title` を渡すと、iOS がその文字を別のテキスト項目として足す**（それがテキストファイルとして保存される）
- 対処: **ファイルを渡す時は `files` だけ**にする（題名は共有シートに要らない＝ファイル名が題名の役をする）
- ⚠ **native の `Share.share` からも先に外した**。アプリ版では未確認だが、**同じ iOS の共有シートに載る以上、同じ罠を踏む可能性が高い**（見えている地雷を、確認できるまで置いておく理由がない）

**設計判断**
- **1ファイルの時も共有シートを使うように広げた**（📄 JSON もスマホでは共有シートへ）。⚠ 理由＝**同じ画面の 📄 と 📊 で出口が違う**（片方はダウンロード・片方は共有シート）と、押した結果が読めない。r63 は「2つ以上の時だけ」という**実装の都合**が UI に漏れていた
  - ⚠ 安全策＝受け取れない形式は `canShare` が false を返す＝**その時は今までどおりダウンロードに落ちる**（できない端末で無言にならない）
- **📤 の案内は「一番短い道」を先に書く形へ**＝「共有シートで Claude / ChatGPT を選べばそのまま手渡し」を先、「Drive に置けば次から書き出さずに済む」を後。⚠ **Drive 経由は消さない**＝溜めておく道と手渡しの道は役割が違う（前者は次回以降が楽・後者は今すぐが楽）

**結果 / 観察**
- ブラウザ実測 green・コンソール 0（`navigator.share` に渡す鍵が `files` **だけ**であること＝余計な .txt の原因が消えたこと／1ファイルも2ファイルも共有シートに乗ること／`canShare` が false の時はダウンロードに落ちること／パソコンは今までどおり2連続ダウンロード＝回帰なし）
- 例文6種は実機で表示を確認（内容の評価は持ち越し）

**教訓**
- **共有シートに渡す `title` は「無害な飾り」ではない**＝渡した文字が**ファイルとして実体化する**。ファイルを渡す時は余計な鍵を足さない
- **実装の都合（「2つ以上の時だけ共有」）は UI に漏れる**。同じ画面に並ぶボタンは、出口を揃える
- **正しい道は、作った道の中にもう一段短いのが隠れていることがある**（Drive 経由を作ったら、同じ共有シートに Claude が直接いた）＝実機で触ってもらうまで見えなかった

**残課題 / 次の方向**
- 実機: 余計な .txt が消えたか／📄 JSON もスマホで共有シートになるか
- 例文6種の中身の評価（ユーザー確認待ち）

## r63 — 📊 CSV 2ファイル同時が web で壊れていたのを直した／🗣 頼み方の例を6種類に (2026-08-15)

**背景**
- r62 で入れた「📊 CSV をレシート＋料理の2ファイルで1回に」が**実機で壊れていた**＝ユーザー報告 **「mealしか保存できません」**（1つ目のレシートが落ちてこない）
- 併せて要望＝**「プロンプト例は豊富にしましょう。分析にあるように6種類用意して」**

**ハマったところ**
- 症状: web で 📊 CSV を押すと、**2つ目（料理）しか保存されない**
- 原因: **同じ瞬間に `<a download>` を2回叩くと、後から始まった方が前をかき消す**ブラウザがある（1つ目が初期化される前に2つ目が始まる）
- 対処: **2つ目の前に 600ms 空ける**。実測で `<a>` のクリックが2回とも発火・間隔も確保
- ⚠ **r62 で「setTimeout を挟むと止められることがある」と書いたのは私の思い込みだった**。blob URL のダウンロードは押した操作の直後でなくても走るので、**間隔を空けるのが正解**だった。**根拠のない保険で正解を先に潰していた**＝r62 の時点で実測していれば防げた

**設計判断**
- **指で触る画面（`pointer: coarse`）では共有シートで2つまとめて渡す**＝そのまま Drive に保存できる＝この機能の目的地に一手で着く。**パソコンはダウンロードのまま**（Windows の共有ダイアログは「フォルダに保存」がしにくい＝目的地から遠ざかる）
- **共有シートを閉じただけの時は「保存しました」と言わない**（出していないのに出したと言わない）。共有そのものが駄目な端末は**ダウンロードに落ちる**（無言で何も起きないのが最悪）
- **例文6種は 📈 の型（AN_PRESETS）と別に持つ**＝📈 はアプリが指示文（AN_SYSTEM）を添えて送るので短くてよいが、**こちらはそのまま貼られて終わり**＝前置きも注意書きも例文の中に入っていないと効かない
- **共通の前後を挟んで組み立てる**（`EXP_PROMPT_HEAD` + 型の本文 + `EXP_PROMPT_FOOT`）＝6つ書き写さない＝**直す時に1つだけ直し忘れる事故**を防ぐ。おかげで「receipt_id が同じ＝1回だけ数える」が**全型に必ず入る**（テストでも全型を確認）
- 型の内訳＝📊ふりかえり / 💡節約のヒント / 🩺健康の面から / 🏪お店のくせ / **⇆前とくらべる** / **📋表とグラフにする**。⚠ 後ろ2つは**この道（ファイルを渡す）でしかできないこと**を入口にした＝📈 は1回きり・800字なので期間をまたぐ比較や表の作成には向かない

**結果 / 観察**
- ブラウザ実測 green・コンソール 0（`<a>` クリック2回と間隔／実データ経路で2ファイル／共有シートの3分岐＝成功・キャンセル・失敗フォールバック／例文6種すべてに前置きと重複よけ／型の保存）
- ⚠ **実機での確定はまだ**＝直したのは「間隔を空ける」だけなので、iPhone Safari が2つ目を拒む可能性は残る（その時は共有シート側に寄せる）

**教訓**
- **思い込みで保険をかけると、正解を先に潰す**。r62 のコメントは実測なしに書いた推測で、それがそのまま bug になった。**「〜すると止められることがある」と書く時は、止められたのを見たのか自問する**
- **1つの機能を2つの道（共有シート／ダウンロード）に分けるなら、どちらを選ぶかは「目的地に近いか」で決める**（できるかどうかではなく）

**残課題 / 次の方向**
- 実機: 📊 CSV で**2つとも**落ちてくるか（iPhone Safari／パソコン）
- 実機: 指で触る画面で共有シートが開き、Drive に2つ保存できるか

## r62 — 📤 書き出しを1次に・📈 は「簡易分析」へ（Drive→AI の手動検証が YES） (2026-08-15)

**背景**
- ユーザーの相談＝「**いちいちデータを AI に渡さなくても、Google ドックスやスプレッドシートに蓄積されて、AI がそれを読みに行く方が楽なのではないか**」
- 答え方＝**コードを書く前に、手で検証**（📤 全期間 → 自分の Google ドライブに保存 → AI アプリにそのファイルを読ませる。ゼロ行で試せる）

**設計判断**
- **Google Drive の自動連携（API・OAuth＝アカウント連携）は今は作らない**。手動の「全期間で出して上書き」で体験が成立すると分かったので、**摩擦が実証されてから**投資する。OAuth はアプリ版で本物のブラウザを開く部品が要る＝そこが工数の本体。加えて「ユーザーの AI が Drive を読めるか」は契約プラン次第＝そこが崩れると投資が無駄になる
- **重なり対策はデータと文言の両輪**＝データ側は receipt_id（r21 から一意な鍵）、文言側は 🗣例文と JSON の `_readme` に「receipt_id が同じ＝1回だけ数える」を明記。さらに**「全期間」で出すと毎回同じファイル名**（receipts_all_all.json）＝ Drive の上書き運用と自然に噛み合う（重なったファイルがそもそも増えない）
- **CSV は2ファイルのまま、手数だけ1回に**＝列が違うものは同じ表に並べない（r41）は不変。native は共有シートに2ファイル同時（Share.share の files 配列）、web は同じタップの延長で2回ダウンロード（⚠ setTimeout を挟むとダウンロードが止められることがあるので挟まない）
- **期間ボタンは 📈 の anPeriodSeg と同じ作法**＋直近7日を追加。選択は `rcpt.exp.period` に保存＝次に開いても同じ期間。日付を打つのは「期間を選ぶ」の時だけ
- **📈 は消さない**＝① APIキーだけで動く道（AI アプリの有料プランが無い人）② その場で手早く確かめる用途。ヘッダの並びは 📤 を 📈 より前へ・📈 の頭に「しっかり分析するなら 📤 → Drive → AI」の案内

**結果 / 観察**
- ブラウザ実測 green・コンソール 0（期間6モードの計算・📤 の開閉・「期間を選ぶ」の初期値・`_readme` の一文・例文の receipt_id・CSV 2ファイル経路の例外なし）
- ⚠ **iOS Safari で連続2ダウンロードが両方成功するかは実機待ち**（だめなら2回目だけ共有シート化などの逃げ道を作る）
- ⚠ native の2ファイル同時共有も実機未確認（アプリ版は r34 以前なのでどのみち先の話）

**教訓**
- **コードを書く前に、体験は手で検証できる**。今回はゼロ行で「基本こっち」の確信まで到達し、そのあと UI を寄せた。r15 以来一度も成功していない 📈 の実キー検証も、この道なら「AI アプリの契約」でほぼ置き換わる＝**いちばん失敗していた機能を、作り込む代わりに降格して解決**

**残課題 / 次の方向**

## r61 — 📈 の案内に「ファイルで渡す」手順を書き足した (2026-08-15)

**背景**
- ユーザー要望＝「**さらにしっかり分析したいときには、ファイル形式で渡したほうがいい**ので、その手順も書き足して」。
- r60 では「🤖 AIに渡す」（＝文章として共有シートに出す）1本しか書いていなかった。⚠ **貼り付けと添付では、その先でできることが違う**のに、その差を書いていなかった。

**設計判断**
- 渡し方を **2本立て**にした＝**① 手軽に渡す**（🤖 AIに渡す・ちょっと聞きたい時）／**② しっかり分析する**（📄 JSON をファイル保存 → AI アプリに添付）。
- ⚠ **「ファイルの方がいい」だけでなく、なぜかを書いた**＝(a) 貼った文章は**会話に埋もれる**が、**添付は残る**ので何度でも読み返させられる (b) **AI がファイルを計算に回せる**ので、合計や割合が**目分量でなく計算**になり、表やグラフも作れる (c) 量が多くても**途中で切れない**。
- 手順は**環境の違いまで書いた**＝ブラウザでは「ファイル」アプリに保存 → AI アプリで **＋ から添付**、アプリ版では **📄 を押すと共有シートが開く**のでそこで選べる（`exportOut` が `IS_NATIVE` で分岐している実装のとおり）。

**ハマったところ**
- 🩹 **書いた注記が web では誤りだった**＝「量が多い時は自動でファイルとして渡します」と書いたが、`shareTextOut` を読み直すと**その切り替えは `IS_NATIVE` の側だけ**で、**ブラウザは常に `navigator.share({title, text})`＝文章のまま**だった。⚠ **ユーザーが今いるのは web** なので、いちばん効く場面で嘘になっていた。→「アプリ版だけは切り替わる／ブラウザでは切り替わらないので②を使ってください」に直した。
- ⚠ r53 で「📈 の一覧は絞りません」と書きかけて実装を読んで気付いたのと**同じ種類**＝**文言は仕様ではなく実装の写し**。書く前に読む。

**結果 / 観察**
- ブラウザ実測 green・コンソール 0（2本立てが本文にある／ファイルの手順3点／向いている理由4点／アプリ版との違い／読み方の同梱／見出しが量に応じて「📄 ファイルで渡して分析」に変わる）。**文言と実装の一致も、`shareTextOut` の中身を実際に読んで確認**した。

**教訓**
- **「どちらでもできます」で終わらせず、どちらが何に向くかを書く**。手順だけ並べると、読む人は**手軽な方**を選び、しっかり分析したい時に力不足に気付けない。
- ⚠ **環境で挙動が違うなら、両方書く**（web とアプリ版）。片方だけ書くと、**もう片方の人には嘘**になる。

**結果 / 観察**

**教訓**

## r45 — 読めなかった返事の「現物」を控える（trunc と parse を分ける） (2026-08-14)

**背景**
- 実キーで 🍽 を書き起こし中（openrouter `qwen/qwen3.8-max`）、**2枚は成功して3枚目でエラー**。画面の文言は `返事を読めませんでした（途中で切れた可能性）` ／ 記録の分類は `返事の形が読めません`。
- 同時に得た観察: **「食事は大きいモデルのほうが精度が高い。一回数円程度」**（r40 で 🍽 のAIを別に選べるようにしたのが効いた）。

**設計判断**
- **根本は「アプリが証拠を捨てていた」**。`res.json()` を直に呼ぶと、パースに失敗した時に**返ってきた本文そのものが消える**（手元に残るのは例外だけ）。だから文言が「切れた**可能性**」という**推測**になっていた＝r30 で決めた「アプリの側が控える」が、**この失敗だけ効いていなかった**。
- `text()` で受けてから自分で `JSON.parse` する形に変えて、**始まり方で3つを見分ける**ようにした:
  - 空 → `empty`（何も返っていない）
  - **`{` や `[` で始まって終わっていない → `trunc`**（AI は書けていて、届く途中で切れた）
  - そもそも JSON でない → `parse`（AI が説明文を返した）
- ⚠ **`trunc` を既存の `cut` に混ぜない**。`cut` は「AI が上限（max_tokens）で書き切れなかった」＝次の手は**別のモデル／短く**。`trunc` は「AI は書けている」＝次の手は**同じモデルで 🔁 やり直す**。**原因が違えば次の手も逆になる**ので、札を分けないと案内が嘘になる。
- **本文の抜粋は 📋 の記録にだけ載せる**（読み取り `failureReport` と 📈分析 `anFailureReport` の両方）。⚠ **画面には出さない**＝普通に使う人には雑音で、必要なのは「同じことが続く時に原因を追う人」だけ＝**押した人だけが見る**形（r30 の 📋 と同じ考え）。
- ⚠ **抜粋は頭と尻の両方を残す**（長い時は中略）。**切れたかどうかは終わり方を見ないと分からない**ので、頭だけ残すと肝心の証拠が落ちる。
- 🩹 **中継ぎの「詰め物」を捨ててから読む**ようにした。待たせている間に空行や `: 処理中` のような行を先に送ってくるサービスがある。⚠ JSON は空行や `:` では始まらないので、**先頭の空行と `:` 行だけ**捨てるのは安全（本文の途中の `:` は触らない＝テストで確認）。

**ハマったところ**
- 🩹 **r44 までは、詰め物つきの返事が「まさにユーザーが見た文言」で落ちていた**（偽の返事を返させて実測）。`: OPENROUTER PROCESSING\n\n{...}` は `res.json()` で必ず落ち、その時の文言が `返事を読めませんでした（途中で切れた可能性）`。**これが原因だったなら r45 で直る**が、⚠ **実際に何が返ってきたかは記録が無いので断定できない**（断定しないことがこの版の主旨そのもの）。次に出た時 📋 に現物が載る。
- ⚠ `errTag` は**上から順に**当たるので、`trunc` の規則を `parse` より**前**に置いた（どちらも「読めなかった」文言なので、順番を間違えると全部 `parse` に落ちる）。

**結果 / 観察**
- ブラウザ実測 **19/19 green**・コンソール 0。内訳＝詰め物の除去5／札の判定4／`trunc` と `cut` で次の手が違うこと1／抜粋の頭と尻4、**偽の返事を `apiFetch` に返させた通しテスト5**（⚠ **正しい JSON が今まで通り読めること**＝回帰確認を含む）。
- 📋 の出力を実際に組み立てて確認＝分類・次の手・**返ってきた本文**が載り、**画面の側には本文が出ない**。

**教訓**
- **推測が書いてあるエラー文言は、たいてい「証拠を捨てている」印**。「〜の可能性」と書きたくなったら、**その可能性を確かめられる材料を、その場で残せていないこと**を疑う。
- **標準の便利な関数が、証拠を食べることがある**（`res.json()`）。**失敗した時に何が手元に残るか**で選ぶ。
- **同じ「読めない」でも、原因が違えば次の手は逆になる**（`trunc`＝やり直す価値がある／`cut`＝やり直しても同じ）。**札を1つにまとめると、案内のどちらかが必ず嘘になる**。
- **実運用のフィードバックは「成功した数」も持ってくる**（2枚は成功・3枚目で失敗）＝**たまに起きる**と分かるだけで、キー・モデル・CORS の線が消えて原因が絞れる。

**残課題 / 次の方向**
- ▶ **次に同じエラーが出たら 📋 を押して貼ってもらう**（今度は現物が載る＝原因が確定できる）。詰め物が原因だったなら、そもそも二度と出ない。
- 🍽 **料理は大きいモデルを使う**（実運用の観察）。⚠ 値段が気になっても**料理を安いモデルに倒さない**＝レシートは「型に嵌める」仕事なので安いモデルでも通るが、料理は「何が写っているか」を見る仕事でモデルの地力がそのまま出る。下げるなら 📷 レシート側。

## r40-r41 — AI を3種類に ／ 📤 で料理の要約・詳細を選ぶ ／ トップに「料理を撮る」 (2026-08-14)

**背景**
- 要望3件。①「期間を指定して書き出しでも、料理の**要約と詳細を選択して**出力できるようにしたい」②「レシート読み取り・食事画像読み取り・分析用と **AI を3種類**設定できるようにしたい」③「トップページに、レシートの写真を撮るに加えて**料理の写真を撮る**を足したい」。

**設計判断（r40＝AI を3種類）**
- **役割を表にした**（`ROLES`）。⚠ **`ocr` は表に持たない**＝あれは「選ばなかった時に落ちる先」で、`meal` / `an` とは意味が違う（あの2つは「レシートと同じ」を選べるが、`ocr` には落ちる先が無い）。同じ形に見えるものを同じ箱に入れると、`ocr` にも「同じにする」選択肢が生えてしまう。
- **落ちる先は常に `getProv()` に固定**＝役割どうしを参照させない（`meal` が `an` を見る、のような輪を作らない）。
- **キーは AI ごとに1本**を3つの役割で共有する（同じ鍵を3回貼らせない）。分かれるのは「どの AI か」と「どのモデルか」だけ。⚠ そのため**キーの欄は「レシートと違う AI を選んだ時だけ」出す**。
- **設定の描画を1本にした**（`renderRoleSettings`）。⚠ 3つ目を足すのに同じコードを3度書くと、次に4つ目が来た時に直す場所が増え続ける。
- **🍽 の画面に「どの AI が読むか」を出した**（📈 の `anAiLine` と同じ形）。⚠ ⚙ に3つ並んだ以上、**使う画面で分からないと迷う**。キーが無ければその場で言う（撮る前に気付ける）。
- 🍽 と 📷 で向くモデルが違う、という前提を画面に書いた＝レシートは「数字を正確に写す」仕事、食事は「見えたものを言葉にする」仕事。

**設計判断（r41＝📤 の選択・トップの入口）**
- **既定は「料理も出す・詳細も入れる」**＝これまでと同じ結果。⚠ **選べるようにする変更で、いままで押していた人の結果を変えない**。
- ⚠ **`.json` では料理をレシートの JSON の**中に**入れる**（`meal_log` という別キー）。r37 で「交換形式に混ぜない」と決めたのは 📈 に渡す**文章**の話で、あちらは2つの塊を並べて書ける。**同じことを .json でやると JSON として壊れる**＝受け取る側が読めない。**同じデータでも、置く場所（文章／ファイル）で正しい形は変わる**。キーを足すだけで `version` は上げていない＝ `receipts` を読んでいる既存の受け手は何も変わらない。

- **🍽 料理のCSV は別ファイル**。⚠ レシートの CSV に混ぜない＝料理には金額の列が無く、同じ表に並べるとどちらの行か分からなくなる（受け取るのは表計算ソフト＝列の意味が全て）。

- **トップの 🍽 で撮ったら 🍽 の画面を開く**。⚠ レシートは一覧がその場にあるので開く必要がないが、料理は**どこに入ったかが見えない**と撮れたのか分からない。

**ハマったところ**

**結果 / 観察**

**教訓**

- **撮り方のコツを1行出す**＝「箸やスプーンなど大きさの分かるものを一緒に写す」。AI が `amount`（茶碗1杯など）を書けるかは、**比べられるものが一緒に写っているか**で決まる。

## r37 — 📈 分析に食事も渡す（既定は要約・深掘りの時だけ詳細） (2026-08-14)

**ハマったところ**

**教訓**
- **同じデータでも、「毎回自動で乗る」場所と「押した時だけ」の場所では既定を変える**。量の心配を誰が持てるかで決まる。

## r36 — 📅 食事の週カレンダー ＋ ドラッグで区分を変える (2026-08-14)

**背景**
- 要望の「**朝食・昼食・夕食・間食カレンダー**」「あとから手動で変更、**ドラッグと項目からの変更どちらのルートからも**」のうち、r35 で作れていなかった2つ（カレンダーとドラッグ）。

**設計判断**
- **縦が日・横が 朝/昼/夕/間食 の 7×4**。⚠ 1日の画面（r35）は消さない＝**役割が違う**。カレンダーは「並びを見て、動かす」場所、1日の画面は「要約を読む」場所。同じものの大小ではない。
- **既定は 📅 週**（要望が「カレンダー」なので）。◀▶ は**見ている画面で進み方が変わる**（週なら7日・1日なら1日）。
- **別の日へも落とせる**。ただし別の日に落とすのは**写真の日付を書き換えること**なので、必ず言う（「📅 8/12 の夕食へ移しました（写真の日付も変えました）」）。⚠ **時刻は動かさない**＝何時に食べたかは写真の側の事実で、動かした先の枠の都合で変えるものではない。
- **ドラッグは追加の道であって、唯一の道にしない**。区分は詳細（r35）からも変えられる＝実機で指が当たらなかった時に、機能ごと使えなくならない。

**ハマったところ**
- 🩹 **ドラッグが1回目の pointermove で必ず死んだ**。原因＝**`<img>` はブラウザが自前でドラッグを始める**（ネイティブの画像ドラッグ）ため、その瞬間に **`pointercancel`** が飛んで、こちらの掴みが指ごと取り上げられていた。`draggable="false"` と CSS の `-webkit-user-drag:none` の**両方**で止めた。⚠ 症状は「掴めるのに動かせない」＝ゴーストは出るのに落とせない、という分かりにくい出方をする。
- 🩹 **`touch-action:none` を掴んだ後に足しても遅い**。ブラウザは**指が触れた瞬間**に「これはスクロールか」を決めるので、250ms の長押しが成立してから CSS を変えても、もうスクロールが始まっている（＝また pointercancel）。**掴んでいる間の `touchmove` を `preventDefault`** して、スクロールが始まらないようにした。
- 🩹 **pointerup のあとに click が来る**＝動かし終えた指を離した瞬間に、その写真の詳細が開いてしまう。直前にドラッグしたかを時刻で見張って握り潰した。
- **長押し 250ms・指が 8px 動いたら掴まない**。すぐ掴むと縦スクロールができなくなり、掴まないと動かせない。この2つは同じ指の動きの取り合いなので、どちらかに倒すのではなく**時間と距離の両方**で分けた。

**結果 / 観察**
- ブラウザ実測 **40/40 green**（r34 の 60/60・r35 の 56/56 も維持）・コンソール 0。ドラッグは**実際にポインタを動かして**確かめている（長押し → 光る → 落ちる → 印が付く／短く触ればタップ／掴む前に動けばスクロール／枠の外で離す）。
- 320px でも 7×4 が横にはみ出さず、枠は写真より狭くならない（56px）。

**教訓**
- **`<img>` を掴ませる時は、まずブラウザに掴ませない**。ネイティブの画像ドラッグは、自前のポインタ処理を静かに殺す。
- **ジェスチャの取り合いは「後から CSS を変える」では解けない**。ブラウザの判断は指が触れた瞬間に済んでいる。あとから割り込むなら、判断そのものを起こさせない（`preventDefault`）しかない。
- **同じ指の動きに2つの意味を持たせる時は、時間と距離の両方で分ける**。片方だけだと、必ずどちらかが使えなくなる。

**残課題 / 次の方向**
- ▶ **実機（iOS Safari）で長押しが当たるか**。⚠ **preview で当たっても実機で当たらない**（r33 の教訓）。特に 38px の写真は小さい。当たらなければ、掴む前に少し拡大する等を考える。
- ▶ **r37 で 📈 分析に食事を渡す**（既定＝要約・深掘りの時だけ詳細）。
- 月の表示（週より広い範囲）は要望が出てから。

## r35 — 🍽 食事の記録（写真 → 要約と詳細の書き起こし → 撮影時刻で自動仕分け） (2026-08-14)

**背景**
- 要望「**朝食・昼食・夕食・間食カレンダー**。食事の写真をUPすると内容を分析記録、事前に登録した時刻により自動で分類。あとから手動で変更も可能（ドラッグと項目からの変更どちらのルートからも）。後で AI で複数日分析するための基礎資料のため、画像を文字起こし保存。**要約と詳細**があるといい。基本は要約を渡し、深掘りの時に詳細を渡せるように」。
- r35 はその土台（記録・自動仕分け・項目からの変更）。**📅 カレンダーとドラッグは r36**、**📈 へ要約/詳細を渡すのは r37**に分けた。

**設計判断**
- **別アプリにせず、レシート spike の中に入れた**。理由＝**同じ機械**（写真 → AI → 記録 → 期間で取り出す → 📈 分析）に乗り、同じ端末・同じ BYOK キーで動く。3つ目の spike を立てると、このプロジェクトが 2026-06-17 に畳んだばかりの**二重管理**を再演する。⚠ ただし**箱は別**（IndexedDB の `meals` ストア）＝金額も店も無く、数え方も違うものを1つの記録に混ぜると、どの操作がどこまで効くのか分からなくなる（r28/r29 で学んだ）。
- **要約と詳細を最初から別のフィールドで持つ**。1つの文章にすると、あとで「渡すたびに全文が乗って高くつく」か「削って深掘りできない」かのどちらかになる。要望の「基本は要約・深掘りで詳細」は**データの形の要求**であって、渡し方の工夫では代用できない。
- **AI に数字を作らせない**。MEAL_RULES で「カロリー・栄養素・グラム数を出すな。量は『茶碗1杯』のように見たまま書け」と明示した。⚠ この記録の用途は**後日まとめて分析するための素材**なので、当てずっぽうの数値が1回混ざると、それを根拠にした分析が丸ごと壊れる（しかも読んだ側は気付けない）。
- **区分は撮影時刻で決める**。⚠ そのため `file.lastModified` は使えない＝iOS のフォトピッカーは HEIC を裏で JPEG に変換するので、**変換した瞬間の時刻**が入ることがある（＝昨日の晩ごはんが全部「いま」になる）。JPEG の APP1(Exif) から **DateTimeOriginal(0x9003)** を自前で読む。⚠ **縮小する前の元ファイル**から読む（canvas に描いた時点で EXIF は消える）。⚠ 何を根拠にしたか（exif / file / now）を記録に残し、画面にも出す＝分類がおかしい時に最初に疑う場所になる。
- **手で決めたものを自動で上書きしない**。⚙ で時間帯を変えた時・詳細で時刻を直した時、どちらも `slotAuto=false`（人が区分を決めた）なら区分は動かさない。⚠ 自動の親切で手直しが消えるのが、この種の機能でいちばん腹立たしい。動かした時は**何件動いたか**を言う（黙って過去が書き換わると、自分の記録なのに信用できなくなる）。
- **撮った写真の日へ移動する**。入る日は撮影時刻で決まるので、見ている日と違うことがある。黙って別の日に入れると「撮ったのに出てこない」＝r32 で検索に踏んだのと同じ罠なので、**その日へ移動して、移動したと言う**。
- **枠は空でも4つ全部出す**。空を隠すと、間食だけの日が「間食しか無い日」ではなく「壊れた日」に見える。

**ハマったところ**
- 🩹 **ヘッダが6個目のボタンで壊れた**。320px（iPhone SE 相当）でボタンだけが幅を使い切り、**🧾 が 6px に潰れていた**（r33 で「切れた文字を出すくらいなら出さない」と決めた場所の再発）。360px 以下で隙間と余白を詰めて解決したが、**実機の絵文字は Chromium より大きい**ので、次に足すならボタンを畳んで隠す方へ倒す。
- 🩹 区分の4つが **3+1 に折り返して**いた（`.seg.wrap` の 28%）＝「間食だけ別物」に見える。1行4つに直し、**行数で見るテスト**を足した。
- 写真を読む入口（`analyze`）が**レシート決め打ち**だった。食事用にもう1本足すと、JSONの頼み方の3段構え（r10）・上限で切れた時の扱い（r17）を全部書き直すことになる → **仕事（job）を差し替えられる1本**にした（`OCR_JOB` / `MEAL_JOB`）。⚠ スキーマは呼ぶたびに作る（r31 の教訓）。

**結果 / 観察**
- ブラウザ実測 **56/56 green**（r34 の 60/60 も維持）・コンソール 0。EXIF は**実バイト列の JPEG を組み立てて**、リトル/ビッグ両方のエンディアンで確かめている（ここを外すと分類が全部狂うため）。
- 取り込み → 書き起こし → 枠に入る、までを本物の道で通した（AI だけ差し替え）。

**教訓**
- **時刻に依存する機能は、時刻の出どころを疑うところから始まる**。`lastModified` は「ファイルの時刻」であって「撮った時刻」ではない。プラットフォームが裏で変換する場所（HEIC→JPEG）では、両者はほぼ確実にずれる。
- **後で AI に読ませるための記録は、AI に数字を作らせてはいけない**。人間なら「たぶん適当だな」と割り引ける数字も、次に読むのが AI だと根拠として扱われる。
- **「自動で決める」機能には、必ず「人が決めた」印を持たせる**。印が無いと、設定を変えるたびに人の判断が消える。

**残課題 / 次の方向**
- ▶ **r36 で 📅 カレンダー（複数日）＋ドラッグでの区分変更**。⚠ HTML5 の drag&drop は iOS Safari で動かないので、pointer events で自前で作る（**実機で指が当たるかは preview では分からない**）。

**教訓**
- **選択肢を増やす機能は、「誰が選ぶのか」を全部数える**。ここでは人（✏️）と AI（スキーマ）の2人が選ぶので、片方だけ増やすと機能として半分死ぬ。

**残課題 / 次の方向**

- コードを見たら、理由はアプリが**持っていた**のに、置き場所が悪くて消えていた:
  - `toast('❌ ' + rec.error)` ＝ **4秒で消える**
  - `rec.error` ＝ 保存はされるが、**🔁 でやり直すと `rec.error = null` で消される**
- つまり「やり直したら直った」時、**なぜ失敗したのかは永久に分からない**。r29 の宿題は、構造上ほぼ達成できないものだった。

**設計判断**
- **控えるのは人の仕事ではない**＝失敗を**履歴として残す**（`rec.errors[]`・時刻／そのままの文言／分類／HTTP ステータス／どの AI・モデル／アプリの版）。⚠ **やり直しても・読めても消さない**。「失敗してから読めた」こと自体が原因を追う手がかりで、成功時に消すと**いちばん知りたい事例が消える**。
- **分類の目的は「次に何をすればいいか」を出すこと**。レート制限（待てば直る）／届かない（回線か CORS）／時間切れ（軽いモデルへ）／キー（⚙）／モデル・URL／AI側の不調／返事が上限で切れた／返事の形が読めない、は**次の手がまったく違う**ので、まとめて「失敗しました」と出さない。
- **`httpErr` に HTTP ステータスを持たせた**。日本語の文言に直した時点で「429 だったのか 500 だったのか」という**いちばん硬い手がかりが消えていた**（文言は将来変わるが、数字は変わらない）。
- **見せ方を3段にした**＝ ① 一覧＝短い理由のチップ（「混み合っています」）＝**開かずに次の手が決まる** ② 詳細＝そのままの文言＋分類＋時刻/HTTP/モデル＋**▶ 次の手**＋これまでの失敗 ③ **📋 この失敗の記録をコピー**＝丸ごと持ち出せる。
- **記録は直近5件で頭打ち**（`ERR_KEEP`）。原因を追うのに5件あれば足り、写真1件が肥え続けない。
- **📋 に API キーは載せない**（載せるのは時刻・文言・分類・HTTP・provider/モデル・版だけ）。テストでも明示的に確かめている。
- toast も「（理由は詳細に残しました）」まで言う＝**消える通知に、消えない場所を書いておく**。

**結果 / 観察**
- ブラウザ実測 **35/35 green**（429/500/通信断/成功の4経路・履歴が積まれる・成功しても消えない・5件で頭打ち・分類6種の言い分け・📋 の中身とキー非混入・**📋 ボタンを実際に押してクリップボードまで**・一覧/詳細の表示・📊/📤 の回帰）。コンソール 0。
- 390×844（iPhone 相当）のスクリーンショットで、一覧のチップと詳細の失敗ブロックが崩れないことを確認。

**教訓**
- **人に宿題を出す前に、アプリが既に持っている情報を探す**。r29 の「文言を控える」は、**アプリが4秒で捨てていたものを人に拾わせる**設計だった。⚠ 手作業の宿題は、たいてい「保存し忘れ」の言い換えになっている。
- **やり直しで状態をリセットする時、何を道連れにしているか見る**。`rec.error = null` は正しく見えて、**唯一の証拠**を消していた。
- **エラーを人間語に翻訳する時は、機械の数字も一緒に残す**。文言は読みやすさのため何度でも書き換わるが、HTTP ステータスは書き換わらない。

**残課題 / 次の方向**
- ▶ **実機で失敗が出たら 📋 を押して貼るだけ**（r29 の宿題はこれで果たせる形になった）。まだ**なぜ失敗したかは未解明**なので、実データ待ちなのは変わらない。

**背景**

## r22 — 🧮 税と数量を正しく持ち、合わないレシートに ⚠ を出す (2026-08-13)

**背景**
- ユーザーが**実データの書き出しを読んで**出した指摘2件。
  - 「**items.price は税抜、total は税込**。tax_rate か total_excl_tax を持たせたほうがいい。**逆にこの照合式はそのまま OCR の自動検算ルールに使える（合わなければフラグ）**。現在日本では税率は8％と10％が混在している」
  - 「**qty が信用できない**。クリエイトの『無添加食器洗いせっけん詰替用』が qty=2 だが、396 を2回足すと検算が崩れる。**396 は行合計**（または誤読）」
- どちらも**アプリの画面では気付けない**。合計は正しく表示されるので、明細と突き合わせて初めて分かる。

**設計判断**
- **意味を決めてから、材料を持つ**。`price` は「**その行の金額＝行の合計**（qty を掛けたあとの数字）」と定義し直し、単価は `unit_price` に分けた。読み取りルールにも「**price に qty を掛けないこと**」と明記。⚠ 定義を決めずにフィールドだけ増やすと、税抜/税込と同じ取り違えを別の場所で作る。
- **税は印字どおりに持つ**＝ `total_excl_tax`（税抜合計）/ `tax`（消費税額）/ `discount`（値引き）/ `price_incl_tax`（明細が税込か）＋ 品目ごとの `tax_rate`（8 or 10）。**日本は8%と10%が混在する**ので、税率はレシート単位ではなく**品目ごと**に持つ。
- ⚠ **計算して埋めない**（読み取りルールに明記）。`total_excl_tax` や `tax` を AI に計算させると、**あとで突き合わせる材料が消える**（自分で作った数字と自分で比べても何も分からない）。
- **指摘どおり、この照合式をそのまま自動検算にした**。3通りの式を材料に応じて使い分ける＝①明細(税込)−値引き ②明細(税抜)−値引き＋消費税 ③明細(税抜)×税率−値引き。加えて「税抜＋消費税＝合計」と「単価×個数＝行の合計」も見る。
- ⚠ **数字は勝手に直さない**。合わないことを知らせて ✏️（r19）へ誘導するだけ。**原本はレシートであってアプリではない**ので、辻褄合わせをアプリがやると原本と食い違う。
- ⚠ **材料が足りない時は「合わない」ではなく「検算しない」**。読めなかっただけの物を間違い扱いすると **⚠ が出っぱなしになって誰も見なくなる**。結果として **r22 以前のレシートは黙ったまま**（税の材料が無いので検算に入らない）＝過去分が一斉に ⚠ になる事故も同時に防げた。
- 端数の許容は式ごとに変える＝印字の税額を使う式は ±2円、税率から計算する式は**品目数**まで（品目ごとに端数が出るため）。

**ハマったところ**
- 🩹 **テストの期待値を自分で計算間違いした**（500×1.08 ＋ 620×1.10 ＝ 1222 なのに 1188 と書いた）。検算の実装ではなく**検算のテストが間違っていた**＝「合わない」と正しく言われて落ちた。皮肉だが、**検算が効いている証拠**でもあった。

**結果 / 観察**
- ブラウザ実測 **19/19 green**。税抜/税込/8%10%混在の3通りが**合えば黙る**／明細と合計のズレ・税抜+消費税のズレ・単価×個数のズレの3種を見つける／**材料不足では黙る**／✏️ で直すと ⚠ が消える／欄を出していない単価と税率が手直しで消えない（`data-` で持ち回る）。
- 書き出しは **version 5**。📈 分析のシステム文にも「price に qty を掛けない」「数える鍵は `receipt_id`」「日付の集計は `date`（`captured_at` は撮った時刻）」を明記した＝**AI が二重計上する道を塞いだ**。

**教訓**
- **「合計だけ合っていれば良い」は、明細を使い始めた瞬間に破綻する**。🩺 健康の型（r16）は品目を読ませる機能なので、品目の意味が曖昧なままだと**AI が間違った前提で語る**。表示が正しいことは、データが正しいことを意味しない。
- **検算は「材料を持つこと」とセット**。合計と明細しか無ければ「合わない」としか言えないが、税率・値引き・単価まで持てば**どこがおかしいか**まで言える。フィールドを増やす価値はそこにある。
- ⚠ **検算の沈黙も設計**。「分からない時に黙る」を先に決めておかないと、警告が意味を失う。

**残課題 / 次の方向**

## r17 — ⏳ 返事が途中で切れる件に対処（実キーで押す前の地ならし） (2026-08-13)

**背景**
- 次の一手＝「**実キーで 📈 を1回押す**」（r15 から持ち越し）。押す手順を出す前に、送信の形を実 API の仕様と突き合わせた。**実キーはユーザーのお金が動く**ので、fetch 差し替えでは出ない種類の不具合を先に潰したかった。
- 見つかったのは **`max_tokens` の意味が変わっていた**こと。既定の Claude Opus 5 は**考えてから答える設定が既定でオン**で、`max_tokens` は「**考えた分＋返事**」の合計を縛る。📈 は effort を指定していない（r15 の意図的な設計）ので考える量は多めになる。

**設計判断**
- **📈 の上限を 4000 → 8000 に**。AN_SYSTEM で頼んでいるのは 800 字程度なので、**実際に使う量＝課金は増えない**（上限は「使う量」ではなく「切れないための余白」）。effort を下げて考える量を削る手もあるが、**r15 で「分析は考えさせる用途」と決めた設計を、実キーで1回も試す前に曲げたくない**ので触らない。実測でトークン数が見えてから判断する。
- **切れた時に、切れたと分かるようにした**。従来は返事が空で返ると「**AI から空の返事が返りました（別のモデルを試してください）**」と出た＝**原因はモデルではなく上限**なので、言われたとおり別モデルを試すと**課金だけ増えて同じ結果になる**。上限が原因の時は「期間を短くするか、別のモデルを」と出し分ける。
- **途中まで返ってきた時は、本文の末尾に「⚠ 上限に達したため、ここで切れています」を足す**。🗂 履歴に**黙って完成品として貯めない**（後から読み返した時に、なぜ話が終わっていないのか分かる）。
- **📷 読み取りも同じ扱い**。上限で切れれば JSON は必ず途中で終わるので、`parseJsonLoose` に渡す前に止めて「読み取りが上限に達しました（レシートが長い／明細が多い可能性）」と出す。従来の「AI の返事を JSON として読めませんでした」だと、**モデルの質の問題に見える**。
- 判定は共通の `isCut()` に寄せた（Anthropic は `stop_reason='max_tokens'` / OpenAI互換は `finish_reason='length'`）。**入口ごとに書き分けない**＝r10 で広げた間口を狭めない。

**ハマったところ**
- 🩹 **これは「実装のバグ」ではなく「モデル側の既定の変化」だった**。r15 を書いた時点の頭では 4000 は十分だったが、`max_tokens` が思考も含む仕様では意味が変わる。**コードを読んでも間違いが見えないタイプの不具合**で、fetch 差し替え（返事を自分で作る）では**絶対に再現しない**。実 API の仕様と突き合わせて初めて見つかった。
- ⚠ ローカル確認は今回も**配信ディレクトリを明示**（`--directory receipt-spike`）。`#btnAnalyze` の有無で「あの日を見ていないか」を先に確かめてから測った（r16 の教訓の運用）。

**結果 / 観察**
- ブラウザ実測（Chromium・390px・fetch で `stop_reason` を偽装）で **12項目すべて green・console エラー 0**（404 は favicon＝HTML に宣言が無く自動要求されるだけ）。
  - ① 空＋上限 → 上限だと分かる文言／結果画面は開かない／**送信の `max_tokens` が 8000**
  - ② 途中まで＋上限 → 結果は開き、本文末尾に注記
  - ③ 通常時 → 注記は付かない・見出し/箇条書き/太字の描画・トークン数表示・🗂履歴に貯まる（回帰）
  - ④ 📷 読み取りの上限 → 「JSON として読めません」ではなく原因が分かる文言

**教訓**
- **`max_tokens` は「返事の長さ」ではなく「モデルが使う量」**。考えてから答えるモデルでは思考も同じ器から出るので、返事の目標文字数から逆算した値は足りなくなる。上限は**課金の上限ではない**（使った分だけ課金される）ので、余白は広めに取ってよい。
- **エラーメッセージが原因を取り違えると、ユーザーはお金を払って同じ失敗を繰り返す**（「別のモデルを試して」に従うと課金される）。BYOK のアプリでは、**文言の正確さがそのまま金額**になる。
- **実キーで押す前に、実 API の仕様と突き合わせる価値がある**。fetch 差し替えは「自分が作った返事」しか返さないので、**相手側の既定が変わったことは原理的に検出できない**。

**残課題 / 次の方向**
- **実キーではまだ 1 回も通していない**（r15 から継続）。次の一手は変わらず「実キーで 📈 を1回」＋「📎 添付つきで1回」。
- 何回か回して**トークン数を実測**し、8000 で足りるか／effort を下げる余地があるかを決める。

- **🍚 食費をくわしく → 🩺 健康の面から**。金額の話は **📊 統計で数字が正確に見える**ので、AI には**アプリが数えられない側**（何を買っているか＝食生活）を聞かせる方が価値が立つ。⚠ 型の文に「**医者の代わりではないので断定しないで**」を入れた（AN_SYSTEM の「説教しない・推測を事実のように書かない」と同じ方向。健康の話は決めつけが一番害になる）。
- **📎 添付＝画像・PDF・テキスト**。健康診断の結果や献立の写真など、**レシートの数字だけでは分からない事情**を同じ依頼に混ぜられるようにした。
  - **添付そのものは保存しない**（履歴には名前だけ）。一度きりの材料で DB を重くしない／「何を見せた上での答えか」は残る。
  - 画像は **1568px に縮小**（vision が見る大きさの目安）。⚠ レシート本体の 2576px と**違う値**なのは、こちらは「印字を読む」用途ではないから（同じ値にすると無駄に高い）。
  - **並びは「添付 → 依頼文＋データ」**＝長い材料を先に、聞きたいことを最後に。依頼文には `（添付: …）` と名前を書き添える（AI が何を渡されたか分かる）。
  - **PDF は Claude だけ**（`document` ブロック）。OpenAI 互換は入口ごとに扱いが違うので、**黙って落とさずその場で断る**（「Claude を選ぶか、画像にしてから渡して」）。
- **⛶ 支出マップの全画面**。46vh だと店のピンが重なって読めないのが動機。⚠ **全画面の間はタブもシートの✕も地図の下**になる＝**出口が ⛶ボタン（✕）だけ**なので、その1つが必ず最前面にあることを検証項目にした。全画面でも**凡例（分類の絞り込み）は下端に重ねて使える**ようにした（拡大して初めて絞り込みたくなるため）。

**ハマったところ**
- 🩹 **テストが「あの日の index.html」を見ていた**＝シェルの作業ディレクトリがリセットされ、ローカルサーバがリポ直下（あの日）を配信していた。「`#list` が無い」「IndexedDB のストアが空」で気づいた。**教訓＝この 1 リポに 2 プロダクトが同居しているので、ローカルサーバは配信ディレクトリを毎回明示する**（`http-server receipt-spike/`）。同じ罠は「あの日側を触っているつもりでレシートを見ていた」方向にも起きる。
- ⚠ **添付が無い時まで `content` を配列にすると互換性が落ちる**。部品の配列は画像/PDF を混ぜるための形で、**文字だけの時は文字列で送るのが最も通る**（r10 で間口を広げた OpenAI 互換サービスには、文字列しか想定していない実装がある）。→ 添付が無ければ r15 と同じ文字列のまま送る。**新機能のために、その機能を使わない人の道を狭めない**。
- 🐛 Leaflet は**容器の大きさが変わっても自分で気づかない**＝全画面の切替で `invalidateSize()` を呼ばないとタイルが元の大きさのまま貼られる（既知だが、今回も同じ場所で必要だった）。

**結果 / 観察**
- ブラウザ実測（Chromium・390px・fetch 差し替え）で **r16 の27項目＋r15 の27項目＋既存回帰16項目＝全 green**。画像が実際に 2400px→**1568px** に縮んで image ブロックで送られること、テキスト添付が本文に混ざること、PDF が Claude では `document`・ChatGPT では**エラーで断られる**こと、全画面で地図が 388px→**844px** になり ⛶ が最前面のままであることを確認。
- 残る console エラーは地図タイル（`basemaps.cartocdn.com`）への到達不可＝**サンドボックスから CDN へ出られないだけ**で、実機では出ない。
- **配布まで到達（2026-08-12）**: main へマージ＝web（GitHub Pages）に r16 が出た。**Codemagic の iOS ビルドも成功**＝TestFlight に r15/r16 入りのビルドが届いた（r14 で通した道が2回目も素直に通った＝パイプラインとして使える状態になった）。Android だけ r13 相当のまま（入れるなら APK 作り直し）。

**教訓**
- 「AI に何を聞かせるか」は、**アプリが自分でできること（数える）とできないこと（解釈する）の線引き**で決まる。金額の集計を AI にやらせると遅くて高くて不正確になるが、**買っているものから食生活を読む**のは AI にしかできない。型（プリセット）はこの線の上に置く。
- 出口が1つしかない UI（全画面）は、**その1つが必ず押せること自体を検証項目にする**。「拡大できる」より「戻れる」の方が壊れると痛い。

**残課題 / 次の方向**
- **実キーではまだ 1 回も通していない**（r15 から持ち越し）。添付つき（健康診断の画像など）で1回試すのが次の一手。
- PDF を OpenAI 互換でも渡したいなら、端末側で PDF → 画像に変換する手がある（pdf.js を同梱＝重い）。要望が出てから。
- 添付を履歴に残すかは保留（今は名前だけ）。「あの時の診断書つきの分析をもう一度」が欲しくなったら考える。

## r15 — 📈 分析＝溜まったレシートをまとめて AI に読ませる（別AI・期間・型・自動保存） (2026-08-12)

**背景**
- r14 の TestFlight が**成功**（iPhone に届いた）。続けてユーザーの要望＝「**レシートを分析する。写真分析とは異なるAIを登録できる。使用するデータの期限を設定できる。プロンプトは、おすすめの型のプロンプトか、自由に設定できる。設定すれば自動に出力は保存して貯めれる**」。
- これまで「溜めたデータを分析する」は **📤 で書き出して AI アプリに手で渡す**運用だった（r8 で決めた手順）。それをアプリの中で完結させる。

**設計判断**
- **📊 統計と 📈 分析は別物として並べる**＝統計は「アプリが数える（正確・無料・即座）」、分析は「AI に読ませて言葉にしてもらう（解釈が要る・お金がかかる）」。片方に寄せない。
- **送るのは 📤 と同じ書き出し JSON（v2・生データのみ）**＝手で Claude に渡すのと**同じ中身**。集計は入れない（ライフログから引き継いだ「交換フォーマットに統計を入れない」原則）。**写真は送らない**＝📷 の読み取りで既に文字になっているので、もう一度画像を送る理由がない（安い・速い）。
- **用途ごとに AI を分けられるようにした**＝ ⚙ の既存の選択は実は「**写真の読み取り**用」だったので**そう改名**し、その下に「**データの分析に使う AI**」を追加。⚠ **キーは AI ごとに1本を読み取りと共有**する（同じ鍵を2回貼らせない）。分けるのは「どの AI か」と「どのモデルか」だけ＝**写真は安いモデル・分析は賢いモデル**が組める。
  - 分析用に読み取りと別の AI を選んだ時だけ、**その AI のキー欄を分析セクションにも出す**。出さないと鍵を登録するために上の選択を一度切り替える必要があり、**読み取り側の設定まで動いてしまう**。
- **期間は実行時点から数える相対期間**（今月・先月・直近30日・今年・全期間・期間を選ぶ）。来月また押せば来月の話になる＝「設定して貯める」使い方と噛み合う。⚠ 逆さま入力を黙って直さないのは統計と同じ作法。
- **押す前に「送るデータ 約N文字」を出す**＝課金は送る量で効くのに、それが見えないまま押させない（15万文字超は警告）。
- **保存ボタンを置かない**＝「設定すれば自動で貯まる」の要望どおり、実行したら黙って 🗂 履歴に入る。チェックを外した時だけ「保存していません」と結果画面に明示する（消えるものを黙って消さない）。
- **AI に説教させない**（AN_SYSTEM）。家計のデータは弱みなので、責める文章が返ると次から開かなくなる＝**データも溜まらなくなる**。「事実と、本人がこれから選べることを短く」と頼む。
- 返事の記法は**見出し・箇条書き・太字だけ**に限定して頼み、その3つだけを描画する小さな変換を書いた（表は使わせない＝スマホ幅で読めないため）。⚠ **必ず先にエスケープしてから記法を戻す**＝モデルの出力を HTML として実行させない。

**ハマったところ**
- 🐛 **`hidden` 属性が効かない**＝保存オフの時に隠すはずの 🗑 削除ボタンが出たまま。原因＝`hidden` は UA の `display:none` なので、作者側の `.btn{display:block}` に**負ける**。→ `[hidden]{display:none !important}` を1行入れて全体で勝たせた（同じ罠が今後も出るため個別対処にしない）。
- 🐛 **⚙ が 📈 の裏に開いた**＝オーバーレイの重なりは z-index が同じなら **DOM の順**で決まり、`ovSettings` は `ovAnalyze` より**前**にある。→ `#ovSettings{z-index:22}` で明示的に持ち上げた（他の重なりは DOM 順で成立しているので触らない）。
- 🐛 **`##` を `<h3>` にしていた**＝AI には「`##` を使って」と頼んでいるのに、それが**いちばん小さい見出し**になっていた。→ `#`/`##` は h2、`###` 以降を h3 に。**頼んだ記法と描画の強調が食い違わないようにする**。
- ⚠ **読み取りと分析が同時に走ると設定が混線する**構造だった＝鍵・URL・モデルを呼び出しの途中で**グローバル（`getProv()`）から読んでいた**ので、分析中に別 AI へ切り替えたり撮影したりすると別の鍵で飛びうる。→ **呼び出しの文脈（`ctx`）を最初に固めて引数で渡す**形に直した（`analyze(ctx, b64)` / `chat(ctx, …)` / `test(ctx)` / `listModels(ctx)`）。**撮影しながら分析、は普通に起きる**ので潰しておく価値があった。

**結果 / 観察**
- ブラウザ実測（Chromium・390px・fetch 差し替え＝実キー無しで送信内容の形を確認）で **📈 側 27項目・既存回帰 17項目すべて green・console エラー 0**（地図タイルの読み込み失敗はサンドボックスから CDN へ出られないだけ）。
  - 確認できたこと＝**分析は分析用の URL・キー・モデルへ飛ぶ**（読み取りの Claude ではなく OpenRouter/DeepSeek へ）／**依頼文とレシート JSON が同梱され、画像は入らない**／結果が見出し・箇条書き・太字で描画される／**再読み込みしても履歴が残る**（IndexedDB v3）／保存オフは履歴が増えない。
  - 回帰＝📷 読み取りは**読み取り用のキー・モデルのまま**（分析用に別 AI を入れても混ざらない）・🔁再分析・🔌接続テスト・🔄モデル一覧・📊統計・💴マップ・📤書き出しすべて通る。

**教訓**
- **既存の言葉が実は別のものを指していた**（⚙ の「分析に使うAI」＝実は写真の読み取り用）。機能を足す時は、**先にあった名前が新機能とぶつからないか**を見る。ぶつかったら**古い方を正しい名前に直す**（新しい方に別名を付けて逃げると、両方とも意味が濁る）。
- 用途が増えた時、**認証情報（鍵）と選択（モデル）は分けて考える**。鍵はサービス単位・選択は用途単位。ここを一緒くたにすると「同じ鍵を2回貼る」か「用途ごとに使い分けられない」のどちらかになる。

**残課題 / 次の方向**
- **実キーでまだ通していない**（fetch 差し替えでの確認まで）。実機で ⚙ に分析用の AI を入れて 📈 を1回押すのが次の一手。
- 分析の**費用が見えない**（送信文字数までは出した）。使ったトークン数は結果に出るので、何回か回してから「1回いくら」を体感で掴む。
- 期間の**プリセットを保存して繰り返す**（「毎月これを実行」）はまだ無い＝設定は覚えるが、実行は毎回手で押す。自動実行はサーバーが要るので、やるなら「開いた時に前回から1か月経っていたら勧める」形。

- ★**いちばん大きな差＝座標の出どころが無い**。ライフログの座標は「買ったときに**自分がいた場所**（位置ログの動線から補完）」だったが、**このアプリには位置ログが無い**（あの日の軌跡を日パックで受ける案は将来）。そこで **「店ごとに1回だけ位置を決めて覚える」店舗マスタ**（IndexedDB v2 の `places`）に置き換えた。決め方は2つ＝ **🔎 印字住所から探す** ／ **地図をタップして手で置く**。1回決めれば**その店の次のレシートにも自動で効く**。
  - この差のおかげで、ライフログの「同じ店が10〜16個に割れるので座標は中央値」という機構は**不要になった**（1店1座標なので散らばりが発生しない）。代わりに「**位置を持たない店**」が増えるので、そちらの導線（未設定リスト）を厚くした。
- **黙って自動でジオコーディングしない**＝住所は「ヒント」であって座標ではない（レシートの印字が本社住所のこともある）。**押した時だけ**外部（OpenStreetMap / Nominatim）へ**住所の文字だけ**を送り、**1秒に1回まで**（規約）・結果は端末に保存。まとめて探す時は**件数と所要秒数を先に見せて確認**する。⚠ ライフログ側は製品化に向けて「ジオコーディングはしない」と決めているので、**この窓口は1関数（`forwardGeocode`）に閉じてある**（native では OS の地名検索に差し替えられる）。
- **名寄せの規則は統計と共有する**（`groupStores`）。最初は「店名｜支店」で素直に集計したら、**同じ店が統計では1軒・地図では2ピン**に割れた（クリエイト 宇津木台店／宇津大台店＝OCRの読み違い）。⚠ **同じ規則を2つ持つと必ずズレる**。
- **マスタの鍵は「書き方ごとに1本」**（`keys`）＝畳んだ代表名を鍵にすると、あとから別の書き方のレシートが増えた時に代表名が変わり、**覚えた位置が迷子になる**（ライフログが店舗マスタで踏んだ罠）。位置を決めたら**その店の全部の書き方に同じ座標を書く**。
- **大きさ＝量（金額／回数）・色＝分類**（分類は量ではないので大きさに使わない）。半径は `√(量)` ＝**面積が量に比例**（半径をそのまま量にすると大きい方が誇張される）。**凡例のタップで分類を絞り込む**。**収入は地図に混ぜない**。
- **入口は 📊 の中のタブ**（📊統計 ⇄ 💴支出マップ）＝期間（月/年/全期間・◀▶）を共有し、同じ期間を見たまま行き来できる。ヘッダにボタンを増やさない。
- **Leaflet は receipt-spike/vendor/ に同梱**（あの日の `vendor/` を参照しない）。⚠ `sync-web.mjs` は receipt-spike 配下しか見ないので、`../vendor` 参照だと**アプリ版でだけ地図が消える**。ASSETS に `vendor` を追加。

**ハマったところ**
- **preview で地図が動かない**（ピンを置いても表示範囲が変わらず、2つ目のピンが `d="M0 0"`＝描画されない）。原因＝`fitBounds`/`setView` のアニメーションが **requestAnimationFrame 頼み**で、preview では rAF が最後まで走らない（memory「preview は実機と違う」の①）。→ **`animate:false`** で一発確定にした（実機でも確実に決まる方向）。
- **凡例や金額/回数を切り替えるたびに地図が勝手に元の範囲へ戻る**。→ **ピンの顔ぶれ（キーの並び）が変わった時だけ** `fitBounds` する（自分で拡大した場所に戻れなくならないように）。

**結果 / 観察**
- preview（375px）で E2E＝地図タブ表示・Leaflet 同梱読み込み・タイル6枚取得・**位置を手で置く→ピンが立つ→未設定が6軒→3軒に減る**・**書き方の違う2レシートが1軒に畳まれ、マスタには両方の鍵が入る**（`クリエイト｜宇津木台店` と `クリエイト｜宇津大台店` に同じ座標）・凡例オフでそのピンが消える・金額/回数でピンの大きさが変わる（48px と 36px）・ポップアップの「📍位置を直す」から編集画面へ・統計タブへ戻れる・横スクロールなし・console エラー 0。

**教訓**
- **移植は「入力の前提」から確かめる**。ライフログの支出マップの中心的な工夫（座標の中央値・2km の散らばり閾値）は**「座標が動線から来る」という前提の産物**で、前提が変われば丸ごと不要になる。移植で写すべきは**判断の理由**であって実装ではなかった（r11 の店名推定と同じ形で2回続けて出た）。
- **外部に何かを送る機能は、窓口を1つにして、押した時だけにする**。そうしておくと「送っていいか」の判断も、native で OS の機能に差し替える時も、1箇所を見れば済む。

**残課題 / 次の方向**
- 実機・実データでの手触り（いま preview のテストデータ9件でしか見ていない）。⚠ **アプリ版で地図を見るには APK の作り直しが必要**（vendor/ を同梱したため）。

## r10 — 🌏 OpenRouter を3択目に＋JSONの頼み方を3段構えに（間口を広げる） (2026-08-10)

**背景**
- ユーザー要望＝「**中国製とか別のモデルを使いたい時はどうすればいい？**」→ 調べると、詳細設定の URL 変更だけでは足りない条件が3つあると分かった＝ ①**画像を読めるモデルか** ②**JSONの型指定に対応しているか** ③**端末から直接呼べるか（CORS）**。①②はアプリ側で手当てできる。

**設計判断**
- **OpenRouter を3つ目のボタンに**（Claude / ChatGPT / OpenRouter）。**鍵1本・URL1つで DeepSeek・Qwen・GLM・Kimi など中国製を含む多数のモデルに届く**＝サービスごとに設定を作り直す手間が消える。互換サービスを使う時の「既定の道」をこれにした。
- **OpenAI 互換の入口をひな形（`openAICompatible`）に factor out**。ChatGPT と OpenRouter は同じ中身で、違うのは URL・鍵の発行ページ・上限パラメータ名だけ（**OpenAI は `max_completion_tokens` / 互換サービスは `max_tokens`**＝ここが地味に割れる）。
- **JSONの頼み方を3段構えに**＝ `json_schema`（厳密）→ `json_object`＋指示文にスキーマ本文 → 指定なし＋指示文のみ。**断られた時だけ次へ落ちる**（キー無効・レート制限・拒否では落とさない＝無駄打ちしない）。**通った形は覚えて次から一発**（`rcpt.fmt.<prov>`）。
- **返事の読み取りを緩く**（`parseJsonLoose`）＝型指定なしのモデルは ```json … ``` や前置きを付けてくるので、素の JSON → コードブロック → 最初の `{` から最後の `}` の順に試す。
- **一覧は画像を読めるモデルだけに絞る**（OpenRouter は `architecture.input_modalities` を返すので `image` を含むものだけ）＝①の条件を UI 側で満たす。返さないサービスでは従来どおり全部出す。
- ③（CORS）は**相手のサーバー次第でアプリ側では越えられない**ので、直さず**分かる文言**に留めた（「APIに届きませんでした」）。

**結果 / 観察**
- ブラウザで偽サーバーを立てて検証＝ ①`json_schema` を 400 で断る相手に対し **自動で `json_object` に落ちて成功**（1回目は2リクエスト・2回目は**覚えた形で1リクエスト**）②```json ``` 付きの返事も正しく読めた ③一覧は画像可のモデルだけ残った（テキスト専用の DeepSeek Chat・音声の Whisper は除外）④ChatGPT 側は `max_completion_tokens` を送る ⑤375px 幅で3ボタンが折り返さず同じ高さに並ぶ。console エラー 0。

**教訓**
- **「対応しているか」を事前に判定しない。頼んでみて、断られたら言い直す。**相手（無数の互換サービス）の対応表を持つのは不可能なので、**失敗の種類で分岐して落としていく**方が現実的だった。しかも通った形を覚えるので、実行時のコストは初回だけ。
- 間口を広げる時は**越えられない壁を正直に線引きする**（CORS）。直せないものを直そうとせず、エラー文言で「これは相手側の都合」と分かるようにした方が使う人が困らない。

**残課題 / 次の方向**
- 実キーでの疎通（ChatGPT・OpenRouter とも未確認）。特に**ブラウザから直接呼べるか**は実測待ち。
- 同じレシートを複数モデルで読ませて、**住所・品目の取れ方と1枚あたりの費用**を比べる（spike らしい次の一手）。

## r9 — 🧠 分析に使うAIを選べるように（Claude / ChatGPT ＋ 詳細設定） (2026-08-10)

**背景**
- ユーザー要望＝「いま AI との連携は Claude だけ。**ChatGPT も Claude みたいに分かりやすく選べる**ようにして。**その他のモデルも詳細設定で**設定できるようにしたい」。r8 までは Anthropic 決め打ち（キー1本・モデル3択）だった。

**設計判断**
- **プロバイダを1つのオブジェクトに畳む**（`PROVIDERS`）。約束は「`analyze(model, 画像base64)` を呼ぶと **JSON文字列と使用量**が返る」だけ。API の形の違い（Anthropic の `output_config` / OpenAI の `response_format`、画像ブロックの書き方、認証ヘッダ）は各プロバイダの中に閉じ込め、**呼ぶ側（analyzeReceipt・接続テスト）は1本のまま**。増やす時はここに1つ足すだけ。
- **キー・モデル・APIのURL は「AIごと」に保存**（`rcpt.key.<prov>` 等）＝両方登録しておいて**切り替えるだけ**で使える。r8 以前の `rcpt.apiKey` / `rcpt.model` は起動時に一度だけ Anthropic 側へ引っ越す。
- **OpenAI のモデルIDを決め打ちしない**。代わりに **`GET /v1/models` で本人のアカウントの一覧を取ってくる**（🔄ボタン・結果はキャッシュ）＋**詳細設定でモデルIDを直接入力**。理由＝モデルは頻繁に増減し、こちらが埋め込んだ ID は必ず古くなる。**「知らないモデルでも使える」形にしておく方が寿命が長い**（Claude 側は実績のある3つを候補として残しつつ、同じ🔄も使える）。

- **接続テストは無料のものだけ**（Anthropic=`count_tokens` / OpenAI=`GET /models`）＝キー確認で課金しない方針を維持。
- fetch 自体が失敗した時（回線なし・CORS 不許可）は**そう分かる文言**にした。ブラウザから直接叩ける保証は相手サービス次第なので、失敗の意味を切り分けられるようにしておく。

**結果 / 観察**
- ブラウザで検証（実キーなし）: ①旧設定の引っ越し ②AI切替でキー/モデル/ラベル/URLが入れ替わり、**戻すと前の値が残る** ③モデルID直接入力が反映 ④**送信内容の形**を fetch を差し替えて確認＝OpenAI は `chat/completions`＋`response_format:json_schema(strict)`＋`image_url(data URI, detail:high)`、Anthropic は従来どおり＝**どちらも同じ `{data, meta}` に着地**。console エラー 0。
- 実キーでの接続テストは本人の手が要る（キー入力は本人のみ）。

**教訓**
- **自分が知らないもの（新モデル）を扱う時は、名前を埋め込まず「相手に聞く」形にする**。モデル一覧の取得＋直接入力にしたことで、こちらの知識の古さがアプリの寿命を縮めない。
- 差し替え可能にするなら**約束（入口と出口）を先に決める**。ここでは「モデルと画像 → JSON文字列と使用量」だけを固定したので、呼ぶ側は一行も変わらなかった。

**残課題 / 次の方向**
- ChatGPT の**実キーでの動作確認**（接続テスト → 一覧取得 → 実際に1枚分析）。ブラウザから OpenAI を直接叩けるか（CORS）は実測で確かめる必要がある。
- 精度・費用の比べっこ（同じレシートを Claude と ChatGPT で読ませて、住所や品目の取れ方を見る）は spike らしい次の一手。

## r8 — 🤖 AIアプリ（Claude）を共有先に出す＝文字で渡す (2026-08-10)

**背景**
- r7 で共有シートは開くようになったが、**共有先に Claude が出ない**（ユーザー「でないですね。でるようにしたいですね」）。このデータの一番の使い道が「AI に渡して分析させる」なので、ここが通らないと書き出しの意味が半分になる。

**原因（推測せず端末に問い合わせた）**
- Android の共有先は **MIME タイプで決まる**。`adb shell dumpsys package com.anthropic.claude` で Claude の受け取り宣言を確認＝ **`image/*` ・ `text/*` ・ `application/pdf` ・ `application/rtf` ・ `application/epub+zip` のみ**。`cmd package query-activities -a SEND -t application/json` は**該当なし**。
- r7 は JSON を `application/json` のファイルで渡していた＝**Claude の受け取り対象外**だったので、そもそも候補に並ばなかった。Drive や Files は `*/*` を受けるので出ていた＝「共有シート自体は動いている」ので気づきにくい。

**設計判断**
- **🤖 AIに渡す＝文字（text/plain）で共有**に変更（旧「📤 共有シートで渡す」を置き換え）。ファイルでなく文字にすると Claude・Keep・メッセージなど text を受けるアプリが全部並ぶ。
- **量が多い時だけ `.txt` ファイルに切り替える**（10万文字を超えたら）。Android の intent は大きすぎると落ちる（TransactionTooLarge）ため。**`.txt` も `text/plain` なので Claude は受け取れる**＝中身は JSON のまま拡張子だけ変える、という割り切り。
- **📄JSON / 📊CSV はファイル共有のまま残す**（Drive・Files への保存用）。役割を「AIに渡す＝文字」「保存する＝ファイル」で分け、📤の画面にその使い分けを表示。
- 📋 コピーは不変（3回連続で触っていない＝どの環境でも効く最後の逃げ道）。

**結果 / 観察**
- 実機で **Claude が共有先に並ぶのを確認**。プレビューに `receipt-spike-export / version 2 / period` が正しく載る。

**教訓**
- **「共有先に出ない」は権限でもバグでもなく、宣言された MIME の不一致**。しかも**共有シート自体は正常に出る**ので「動いているのに目的のアプリだけ無い」という分かりにくい形になる。→ **相手アプリが何を受け取ると宣言しているかは端末に聞ける**（`dumpsys package <pkg>` / `cmd package query-activities`）。推測でフォーマットを試すより速くて確実。
- 渡す相手（AIアプリ）の都合が、こちらのデータ形式の選択（JSON ファイル vs 文字）を決めた。**交換フォーマットは「正しさ」だけでなく「相手が受け取れるか」で選ぶ**。

**背景**
- 実機確認③。**📋 コピーだけが効き、📤 共有シートと 📄JSON/📊CSV ダウンロードは押しても無反応**（ユーザー実機FB）。r4 で「WebView は DownloadListener 未実装だと `<a download>` が無反応」と予想し📋コピーを命綱として先に用意していた線が、そのまま当たった。

**設計判断**
- **native だけプラグイン経由に差し替え、web の経路は触らない**。`exportOut(name, text, mime)` を出口に一本化＝`IS_NATIVE ? 共有シート : download()`。
  - 中身: `Filesystem.writeFile({directory:'CACHE'})` → `getUri()` → `Share.share({files:[uri]})`。**キャッシュなので権限は不要**（`file_paths.xml` に `cache-path` が既にある＝Capacitor 既定のまま使える）。**権限は INTERNET のみを維持**。
- **📄JSON / 📊CSV もアプリ版では共有シートに寄せた**。Android のアプリから共有ダウンロードフォルダへ直接置くのは scoped storage で塞がれており、**「保存」の正しい出口が共有シート**だから。ボタンの意味は「形式を選ぶ」に変わるので、📤 の画面に**アプリ版のときだけ**その説明を出す（黙って挙動を変えない）。
- **📋 コピーは1行も触らない**。唯一効いていた逃げ道を、直している最中に壊さないため。
- 共有シートを閉じただけの時（cancel/abort/dismiss）は**黙る**＝失敗トーストを出さない。

**結果 / 観察**
- 実機（Pixel 7a）で **3手段とも動作**＝ユーザー確認「どれもよさそうです」。**実機確認③クリア**。
- ②分析も同日クリア＝実物のレシートから「クリエイト 八王子宇津木台／食費／¥1,381」を取得（店名・支店・カテゴリ・金額）。

**教訓**
- **逃げ道を先に作っておくと、本命が全滅しても検証が止まらない**。r4 で📋コピーを入れておいたおかげで「データを外に出せない」最悪の状態にならず、原因究明に時間を使えた。
- WebView は「ブラウザとほぼ同じ」ではない。**ブラウザにあって WebView に無い API（ダウンロード・Web Share）は、native プラグインで置き換える前提で設計する**。

**残課題 / 次の方向**
- 実機4点の④（**アプリを閉じて数日後もデータが残るか**＝ITP 対応の答え合わせ）だけが時間待ち。
- 🖼 選ぶ（複数枚）の経路は未検証。

## r5・r6 — 📷 実機でカメラが開かない（写真ピッカーに落ちる）を2段で解消 (2026-08-10)

**背景**
- r4 の宿題「実機で4点確認」の①。Pixel 7a に debug APK を入れて「📷 レシートを撮る」を押したら、**カメラではなく Google フォトの写真ピッカーが開いた**。r4 で「CAMERA を宣言しないのが正解」と読み切ったつもりだったが、実機は別の所で外れていた。

**原因は2つ重なっていた（順に潰した）**
1. **`capture` と `multiple` は同居できない**（r5）。入力欄が `<input type="file" accept="image/*" capture="environment" multiple>` で、**`multiple` があると Chromium が `capture` を無視する**（「複数選ぶ」と「その場で撮る」は両立しない）。結果 `FileChooserParams.isCaptureEnabled()` が false → Capacitor はカメラ分岐にすら入らずピッカーへ（`BridgeWebChromeClient.onShowFileChooser` の 282-287 行）。→ **入口を2つに分離**＝📷 撮る（capture・1枚）と 🖼 選ぶ（multiple・複数可）。処理関数は共通。
2. **Android 11+ のパッケージ可視性**（r6）。r5 でカメラ分岐には入ったが、今度はログに `Capacitor/FileChooser: Media capture intent could not be launched. Falling back to default file picker.`。Capacitor は `resolveActivity(ACTION_IMAGE_CAPTURE)` が null なら諦める作りで、**マニフェストに `<queries>` が無いとカメラアプリが「存在しない」ように見える**。→ `<queries><intent><action android:name="android.media.action.IMAGE_CAPTURE"/></intent></queries>` を追加。**これは可視性の宣言であって権限ではない＝INTERNET のみのまま**。

**結果 / 観察**
- r6 適用後、📷 タップで前面が `com.google.android.GoogleCamera/…CaptureActivity` に切り替わるのを実機で確認＝**カメラが開く・権限ダイアログも出ない**（r4 の「CAMERA を宣言しない」判断自体は正しかった）。
- ついでに **ボタン2つで「レシートを撮る」が2行に折り返す**のを修正。`#shoot` が `left:50%+translateX(-50%)` だと**使える幅が画面の半分**しかない（fixed の shrink-to-fit）。`left:0; right:0; justify-content:center` に変え、帯がタップを吸わないよう `pointer-events:none`（ボタンだけ `auto`）。
- ステータスバーの重なりは**起きていない**（あの日で苦労した所。ヘッダは時計/電池の下に収まっている）。起動時に `Error injecting safe area CSS` の警告は出るが実害なし。

**教訓**
- **フレームワークの実装を読むだけでは足りない**。r4 は Capacitor の `isMediaCaptureSupported()` を正しく読んだが、**その手前（Chromium が capture を落とす）と、その先（intent が解決できない）**で二重に外れていた。web の属性・フレームワーク・OS の3層すべてを通らないと動かない機能は、**実機のログが唯一の審判**。
- ログの読み方: 「警告が出ない」ことも情報だった。1回目は `Media capture intent could not be launched` が**出ない**＝カメラ分岐に入っていない＝原因は手前（属性）と特定できた。2回目は同じ警告が**出た**＝分岐には入った＝原因は先（intent 解決）に移った。**同じ症状（ピッカーが開く）でも、ログの有無で層を切り分けられる**。
- 無線デバッグ（ワイヤレス ADB）が効いた: 手持ちのケーブルが充電専用でも実機検証は止まらない。ペア設定は端末の「専用コードによるデバイスのペア設定」→ `adb pair IP:ポート コード` → `adb connect IP:別ポート`。

**残課題 / 次の方向**
- 実機4点のうち①だけ済み。**②分析（⚙でキー登録→🔌接続テスト→実際のレシートを撮る）③書き出し3手段のどれが効くか ④数日後もデータが残るか** は本人の手が要る（APIキー入力・現物のレシート）。
- 🖼 選ぶ側は未検証（写真ピッカーが開くところまでは確認済み＝r5 前の挙動と同じ経路）。

## r4 — 📱 Android native 化で ITP を根本回避（Capacitor・直接APK配布） (2026-08-10)

**背景**
- r3 で見つけた **iOS Safari の ITP（7日間開かないとサイトデータを削除）** への対応。ユーザー判断＝「**対応だけしたい**。ネイティブアプリか、ログインか。ログインだとデータがサーバーに置かれる、それはまずい。Android端末を持つ知り合い向け、だから端末直接アプリインストール」。

**設計判断**
- **ログイン方式を却下**（ユーザー判断を支持）＝ ITP は「サイトデータを消される」問題であって「データが端末にある」ことが原因ではない。サーバーに逃がすと**ローカル完結という spike の検証目的そのものが壊れる**。native 化なら同じデータをアプリ領域に置くだけで解決＝方針を1ミリも曲げずに済む。
- **Capacitor で Android 化**。あの日の基盤（Capacitor 8・compileSdk 36・sync-web の流儀）をそのまま踏襲、ただし **appId・アプリ名・android プロジェクトは完全に別**（v233 の「別アプリ」決定どおり）。
- **CAMERA 権限は宣言しない**。Capacitor の `BridgeWebChromeClient.isMediaCaptureSupported()` を読んで確定＝`hasPermissions(CAMERA) || !hasDefinedPermission(CAMERA)`。つまり**宣言しなければ許可不要**でOSのカメラアプリを intent 起動できる。宣言すると実行時許可が必須になり、要求コードを持たないこのアプリでは撮影が壊れる。**権限は INTERNET のみ**＝知り合いに配る時の説明も簡単。
- **配布は debug APK の直接インストール**。サイドロードに署名の種類は関係なく、リリース鍵の管理が消える。⚠ 更新時は versionCode を上げる／同じPCでビルドする（署名が変わると上書き更新できない）。
- **📋 コピー書き出しを追加**。native WebView は `<a download>` も Web Share API も効かない可能性がある＝データが端末に閉じ込められるのが最悪のシナリオなので、クリップボードという**必ず効く逃げ道**を先に用意した（プラグイン不要）。

**調べたこと（Android デベロッパー確認）**
- あの日の TODO に「2026年9月までに登録しないと認定済み端末にインストール不可（＝Play 以外で配信するアプリの話）」というメモがあり、**まさに今その"Play 以外で配信"を始める**ので確認した。結果＝**開始は 2026-09-30 でブラジル/インドネシア/シンガポール/タイのみ・グローバルは2027年**、かつ**確認済み開発者は直接配布の自由を維持**。オーナーは 2026-07-10 に本人確認済み → **当面そのまま通る・日本は第一弾外**。将来は Play Console で「Play 外配信アプリ」として登録すれば継続できる。

**教訓**
- **制約に見えたものが方針を変えさせるとは限らない**。ITP は「サーバーに置け」という圧力に見えるが、実体は「ブラウザの器を使うな」でしかなかった＝器を変えるだけでローカル完結を守れた。制約を読むときは**それが本当に何を禁じているか**まで降りる。
- 権限は「足す」より「足さない方が動く」ことがある（CAMERA）。フレームワークの実装を読んで確かめる価値があった。

**残課題 / 次の方向**
- **実機で4点確認**（撮影が開くか／分析／**書き出し3手段のどれが効くか**／数日後もデータが残るか）。書き出しが全滅なら Share/Filesystem プラグイン導入を r5 で。
